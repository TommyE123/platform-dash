## Summary

Implement a stable TrainRepository interface and working MockTrainRepository to provide the foundational data contract for the PlatformDash widget. This enables UI development to proceed independently of live UK rail API integration decisions. The repository will provide departure data for London Bridge (LBG) to Redhill (RDH) with support for bidirectional queries (swap direction). Mock data includes delayed and cancelled trains to validate UI state rendering rules.

# Phase 0: Outline & Research

## Research Questions & Decisions

### Q1: Which language and runtime?
**Decision**: Kotlin (JVM 11+) as the primary language, with option to transpile or wrap for Android if needed.
**Rationale**: Kotlin is the recommended language for Android development and provides interoperability with Java. This allows the library to be shared across Android app, widget, and backend services if architecture evolves.
**Alternatives Considered**:
- Pure Java: More verbose, less safe. Rejected.
- Multiplatform Kotlin (KMP): Adds complexity for a v1 library. Defer to Phase 3 if needed.

### Q2: Synchronous vs. Asynchronous API?
**Decision**: Synchronous (blocking) `getNextDepartures()` for Phase 1.
**Rationale**: Simpler contract, easier to test. Future versions can wrap with Coroutines or RxJava at the UI layer.
**Alternatives Considered**:
- Coroutines-based (suspend): Adds dependency and complexity early. Defer to Phase 2 UI work.
- Callback-based: More boilerplate. Not recommended for modern Kotlin.

### Q3: How should the mock data be structured?
**Decision**: Hard-coded data in the MockTrainRepository class, organized by route (LBG→RDH, RDH→LBG).
**Rationale**: Deterministic, zero-dependency, easy to customize for testing. No need for external files or databases for mock.
**Alternatives Considered**:
- JSON/YAML files: Adds file I/O. Unnecessary for Phase 1 mock.
- Room database mock: Overkill for mock data. Defer until live API integration.

### Q4: Error handling approach?
**Decision**: Return empty list on invalid routes; no exceptions thrown. Use data class fields to indicate status (ON_TIME, DELAYED, CANCELLED).
**Rationale**: Follows functional style. UI can handle empty lists gracefully. Status field provides all info needed for display rules.
**Alternatives Considered**:
- Throw exceptions: Complicates callers. Return values are safer.
- Result<T, E> type: Adds complexity. Empty list is sufficient for Phase 1.

### Q5: Timezone handling?
**Decision**: Use ISO 8601 OffsetDateTime for all times. Mock data will use UK time (UTC+0 or UTC+1 depending on DST, represented as ZoneOffset.of("+00:00") or "+01:00").
**Rationale**: Unambiguous, standard for financial/transport systems. Widget can display in local user timezone.
**Alternatives Considered**:
- String timestamps: Fragile, parsing errors. Avoid.
- Local times: No timezone info. Dangerous for multi-region apps.

# Key Design Decisions Summary

| Decision | Rationale | Alternatives |
|----------|-----------|--------------|
| Kotlin 11+ language | Modern, Android-native, safe type system | Java (verbose), KMP (premature) |
| Synchronous API | Simpler contract, easier to test v1 | Async/Coroutines (defer to UI layer) |
| Hard-coded mock data | Deterministic, zero-dependency, easy to debug | JSON files (overkill), Room (premature) |
| OffsetDateTime timezone | Unambiguous, ISO 8601 standard | Strings (fragile), LocalDateTime (dangerous) |
| Empty list on error | Functional, UI-friendly | Exceptions (cumbersome), Result type (adds complexity) |
| Route-based organization | Clear, testable, mirrors real API design | Single flat list (hard to maintain) |
